This receipt records the Android emulator, iOS Simulator, live laptop camera, and desktop Safari work after
[QA-2026-09-30.md](QA-2026-09-30.md). It covers the source tree committed with this file.
All services and builds were local. Emulator observations are not physical-phone acceptance.

## Android Pixel Fold API 36

The Fold booted without the launcher hang seen on 30 September. Android Chrome opened the
production launcher at `http://10.0.2.2:3000/` and rendered its game library. The controller
route rendered its unassigned “Ready to connect” state on the Fold's outer display in portrait
and landscape, without visible horizontal clipping. This does not exercise a paired role.

The previously installed debug APK was stale and crashed because it lacked ExpoAudio. A fresh
`npm run native:android` build installed and launched the current 101 Link native UI. Its full
`101L2` deep link reached WebRTC remote-description, answer creation, local-description, and ICE
gathering in `logcat`. Connectivity still did not complete through the emulator NAT, as described
in [emulator-qa.md](emulator-qa.md). A physical same-LAN phone remains necessary for an
end-to-end controller receipt.

The native manual-entry flow exposed a real inconsistency: the LAN testing guide called the
six-character room code a usable pairing code, while 101 Link requires the full connection link
or `101L2` ticket. Before the fix, entering a room code produced the raw error `Invalid URL`.
A regression test failed against that implementation. The app now gives a clear full-link/QR
instruction, and the guide and physical test sheet use the actual pairing path. The rebuilt
native UI displayed that message next to the input on the Fold's short landscape outer display.
Malformed pasted URLs now receive the same readable recovery instruction instead of `Invalid URL`;
that regression was also observed failing before the fix and the replacement message was visible
in the running native app.

## iOS Simulator native Link

The current iOS debug app built and launched on an iPhone 17 Pro Simulator (iOS 26.5).
Using a full Slashstorm `101L2` ticket, the app completed WebRTC signaling and joined
the local host as `SWORD-ONE`; the host showed one Link controller and the app showed
the BLADE pad and SLASH action with 1–3 ms displayed latency at first connection.
The role stayed assigned after Home and reopening the app. The headless Chrome host
required `--disable-features=WebRtcHideLocalIpsWithMdns` for this simulator connection:
its default offer contained only mDNS host candidates, while the working offer exposed
LAN IP candidates. This was a QA harness flag, not a product configuration change.
It does not prove same-LAN physical-phone pairing or network-loss recovery.

Rotating the paired app to portrait exposed a clipped handedness button. The original
portrait screenshot showed its right edge outside the screen. The panel metadata now
stacks in portrait, leaving the full button visible. In the running simulator, tapping
it changed the accessible label from “Use left-handed control layout” to “Use
right-handed control layout” and swapped BLADE and SLASH sides. The existing
landscape row still fit after rotation. The changed TypeScript passed native typecheck
and loaded through Metro on the previously compiled debug app. A repeat Expo Xcode
build stalled while its SDK stat-cache helper remained idle. Running `xcodebuild` with
`SDK_STAT_CACHE_ENABLE=NO` completed both the iOS Simulator and physical-iPhone target
builds. The initial physical build was unsigned because this Mac had no Apple
code-signing identity. A later Personal Team signing pass completed and installed on
the physical iPhone; see the follow-up below. This remains simulator UI evidence,
not a physical thumb-reach or haptic receipt.

## Follow-up: empty-frame inference and physical iPhone access

With no person in view, Vision Lab showed an active, live 960×720 camera track but
zero input frames and no inference samples. The pose adapter's `ingestPoses([])`
correctly emits no player frame when there is no player; Vision Lab had tied its
timing count to that player diagnostic. A focused regression failed against the
previous implementation. The adapter now reports each completed body inference
independently of player detection, and Vision Lab displays “NO BODY DETECTED”
instead of “CAMERA OFF” while the stream is active. The regression passes.

On the rebuilt app, Headless Chrome 154 with 4× CPU throttling reached 120/120 body
inferences on the Mac: mean **14.0 ms**, median **8.7 ms**, P95 **12.6 ms**, range
**6.0–571.9 ms**. The camera track was the physical iPhone 16 Pro's Continuity
Camera at 960×720; the inference ran on the Mac, not on the phone. Chrome exposed
only that camera to this automated session even though macOS also listed the built-in
camera. No person performed the placement and gesture walkthrough, so the full
throttled acceptance case and physical-phone inference case remain open.

The paired physical iPhone (iOS 26.6.2) was reachable through CoreDevice. Safari
was launched with a full local controller link, but no completed connection or game

## Follow-up: physical iPhone Link connection

The owner trusted the Apple Development profile on the iPhone 16 Pro (iOS 26.6.2).
CoreDevice then launched the signed `com.oneohone.link` debug build successfully.
The app received Local Network permission, discovered the Mac's Metro server at
`192.168.0.5:8081`, and loaded the current JavaScript bundle. With the Mac host and
Hub running locally at `192.168.0.5:3000` and `:10101`, respectively, a fresh full
Slashstorm `101L2` ticket was passed through the app's deep link. The Mac host
displayed **1 Link controller** and the iPhone displayed its assigned **SWORD-ONE**
layout with BLADE and SLASH, plus a live latency value (15 ms on the first observed
screen). This is a physical same-LAN signaling, WebRTC, and role-assignment pass.

Sending 101 Link to Home made the host release it after the timeout; reopening the
app restored **1 Link controller** and retained the SWORD-ONE layout. Terminating
and relaunching the app through CoreDevice showed Connecting followed by the same
layout with a fresh latency value (9 ms), without re-entering a ticket. This is a
physical background and process-restart reconnect pass. The run used the source at
`6c2a259` (later commits through `b9a24c1` changed documentation only).

The host run completed without a verified phone touch changing its score. iPhone
Mirroring displayed the control surface but rejected simulated taps, so basic
gameplay input, thumb reach, two-touch use, rotation, and haptic feel are still
pending. The brief iPhone-in-use interval ended Mirroring; it was not a network-loss
test. Safari's physical controller, Android hardware, and installed PWA upgrade
remain open as separate cases.
