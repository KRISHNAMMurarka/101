# Device and signal platform research

Research date: 1 October 2026. Repository baseline: `9c422e21b7b1d33e323f100436fc29963af7c43c`.

This is a source-backed design input. It adds no device support and records no new physical tests. The proposed architecture is in [the design](../superpowers/specs/2026-10-01-universal-device-platform-design.md); the first bounded migration is in [the foundation spec](../superpowers/specs/2026-10-01-device-foundation-design.md). Existing device evidence remains in [the QA record](../QA-2026-10-01.md).

## What the existing code proves

| Existing boundary | Useful foundation | Limitation for the proposed platform |
| --- | --- | --- |
| `packages/input/src/index.ts` | Input adapters, per-device sequencing, held-input release, semantic actions/axes/vectors/poses | A game input vocabulary; normalized axes cannot preserve arbitrary measured quantities |
| `packages/protocol/src/index.ts` | Validated v2 messages, negotiated 24-byte `input-q1`, reliable control, disposable realtime, peer-bound routes | Depends on game InputFrame; small fixed capability list; no general stream/resource protocol |
| `packages/session/src/index.ts` | Liveness, capabilities, role assignment, reconnect | Depends on GameControllerRole; player seats are not general resource ownership |
| `packages/pairing`, `packages/hub-server` | Expiring invitations, distinct host/join/peer authority, bounded signaling state | Trusted-LAN HTTP; no global identity service or internet deployment proof |
| `packages/hardware`, `adapter-hid`, `adapter-bluetooth`, `adapter-serial` | Explicit profiles, byte framing, chooser permissions, disconnect cleanup | Device bytes still become game controls; no universal vendor/device decoder |
| `packages/vision`, `packages/motion` | Local algorithms and calibrated interpretation | Need independent processor descriptions, provenance and typed output contracts |
| `apps/controller-native`, `apps/watch-*`, `apps/desktop-hub` | Real OS target projects | Builds, simulator evidence and physical evidence differ; support is not universal |
| `docs/DEVICE-ROUTING.md` | Separates simulation from display/audio subscriptions | Remote views and selective media/output routing remain a design |

The separation is incremental. Existing parsers, release behavior, transports and tested game semantics should be retained while a new general contract is introduced beside them.

## A tree for browsing, facets for interoperability

The following taxonomy is our design synthesis, not a compatibility catalog.

```text
Resources
├── Human input
│   ├── pointer, relative motion, touch contacts, pen, wheel
│   ├── key transitions, text composition, buttons, gamepad axes
│   └── derived gestures, gaze, posture, voice intents
├── Measurements
│   ├── motion: acceleration, angular velocity, orientation, vibration
│   ├── spatial: position, distance, depth, pressure, force, strain, torque
│   ├── environment: temperature, humidity, moisture, light, air/gas quality
│   ├── material: mass, flow, level, conductivity, pH, particulate count
│   ├── electrical: voltage, current, power, energy, frequency
│   └── physiological: separately permissioned vendor/standard measurements
├── Media and surfaces
│   ├── camera/depth frames, microphone samples, encoded audio/video
│   ├── application view, screen capture, render surface, audio output
│   └── printer document/job, camera/DVR recording and playback
├── Commands and feedback
│   ├── haptic patterns, lights, LEDs, IR transmission
│   ├── switches, relays, motor/servo targets, valves
│   ├── camera focus/exposure/PTZ, audio gain, display properties
│   └── authorized application operations and terminal sessions
└── Processing
    ├── calibration, conversion, filtering, resampling, fusion
    ├── pose/gesture/sound interpretation, mapping, thresholds
    └── application logic with declared input/output schemas
```

Each item also has independent facets: execution host, form factor, attachment, protocol/profile, behavior, schema/units, permissions, ownership, evidence and processing provenance. A ring and a watch may share a BLE measurement profile while offering very different vendor access. A phone can simultaneously be an input source, display, microphone and gateway. An appliance without software can be represented by a gateway, with the gateway's authority and feedback limits recorded.

Thousands of products should reuse protocol and semantic profiles. Unknown products retain unknown capabilities until a profile, documented vendor API or explicit user configuration supplies them. Product labels, MAC addresses and OS guesses are not authority.

## Official ecosystem evidence

| Ecosystem / technology | What an adapter may use | Boundary supported by the official source |
| --- | --- | --- |
| Browser HID | Selected reports/collections | The chooser and protected usages constrain access. Ordinary pointer/key events are different from raw peripheral access. [WebHID](https://wicg.github.io/webhid/index.html) |
| Apple native Bluetooth | Services and characteristics | Core Bluetooth access and background behavior are platform controlled. A service/profile must define meaning. [Core Bluetooth](https://developer.apple.com/documentation/corebluetooth) |
| Android companion devices | Consent-based Bluetooth/Wi-Fi association | Pairing does not itself establish connection or continuous scanning. [Companion pairing](https://developer.android.com/develop/connectivity/bluetooth/companion-device-pairing) |
| Apple Watch | Paired watch/phone messages and transfers | WatchConnectivity joins the companion apps; it is not a general watch-to-anything socket. [WatchConnectivity](https://developer.apple.com/documentation/watchconnectivity) |
| Wear OS | Paired Android/Wear app data | Matching package/signature requirements apply; transport can involve Bluetooth or servers. [Data Layer](https://developer.android.com/training/wearables/data/overview) |
| Rings, bands, earbuds, hearing devices | Available standard profiles or vendor services | Bluetooth has distinct adopted profiles; a wearable form factor proves no particular sensor access. [Bluetooth specifications](https://www.bluetooth.com/specifications/specs/) |
| Wired/wireless headsets | OS audio input/output routes | Available inputs depend on session category/mode. Treat microphone capture and playback separately. [Apple audio inputs](https://developer.apple.com/documentation/avfaudio/avaudiosession/availableinputs) |
| Cast receivers / TVs | Sender/receiver application sessions | Receiver applications define behavior; multiple senders can share a session. This is not unrestricted TV OS control. [Google Cast](https://developers.google.com/cast/docs/overview) |
| External display / AirPlay | Application scenes on a connected display | A display scene is an app output surface. [Apple connected displays](https://developer.apple.com/documentation/uikit/presenting-content-on-a-connected-display) |
| Printers | IPP jobs, formats, media and discovery | IPP Everywhere specifies IPP and DNS-SD interoperability. Older printers may need a print-server/vendor adapter. [IPP Everywhere](https://www.pwg.org/ipp/everywhere.html) |
| Cameras, DVRs, NVRs | Queried media, imaging, event and optional control features | Profile requirements and feature support must be checked for each endpoint. [ONVIF Profile T](https://www.onvif.org/profiles/profile-t/) |
| Matter appliances | Commissioned attributes, commands, events | Matter supports Wi-Fi/Thread/Ethernet; BLE is used for setup. Zigbee needs a bridge rather than direct protocol compatibility. [Matter FAQ](https://csa-iot.org/all-solutions/matter/matter-faq/) |
| Thread | IP reachability through a border router | Border routing and service discovery do not determine application semantics. [OpenThread Border Router](https://openthread.io/guides/border-router) |
| IR legacy controls | Carrier frequency and timing-pattern emission | The emitter API does not provide appliance-state confirmation. [ConsumerIrManager](https://developer.android.com/reference/android/hardware/ConsumerIrManager) |
| Modbus serial/TCP | Register operations plus a device profile | Register semantics/scaling remain profile-specific; Modbus Security is a separate TLS/X.509 specification. [Modbus specifications](https://www.modbus.org/modbus-specifications) |
| CAN / CANopen | Higher-layer device profiles | Generic profiles cover I/O, measuring, drives, encoders, energy and weighing; raw CAN is not sufficient meaning. [CiA profiles](https://www.can-cia.org/can-knowledge/generic-device-profiles) |
| OPC UA | Endpoint discovery and authorized information models | Discovery precedes security/session checks; it does not grant read/write authority. [Discovery services](https://reference.opcfoundation.org/specs/OPC-10000-4/5.5) |
| ROS 2 / DDS | Typed topics/services with compatible QoS | History, reliability and publisher/subscriber compatibility matter. [ROS 2 QoS](https://design.ros2.org/articles/qos) |
| Windows system pointer | Native SendInput adapter | Input injection has integrity-level restrictions. [SendInput](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput) |
| Linux system pointer | Permissioned native virtual input or desktop portal | uinput creates input devices; desktop portal remote control has a session/permission flow. [uinput](https://docs.kernel.org/input/uinput.html), [RemoteDesktop portal](https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.portal.RemoteDesktop.html) |
| macOS system pointer | Native event posting and platform permission checks | Native Core Graphics event APIs exist; the adapter still needs its OS authority and verified behavior. [CGEventPost](https://developer.apple.com/documentation/coregraphics/cgevent/post%28tap%3A%29?language=objc) |

Consoles and closed vendor platforms remain research/adapter candidates until a permitted runtime and API are established. Proprietary radio, old analog audio/video and mechanical devices require appropriate hardware gateways. This research establishes no console, arbitrary ring, DVR or industrial device compatibility.

## Description and discovery standards

WoT Thing Description supplies machine-readable properties, actions, events, schemas, protocol bindings and security descriptions. We should provide import/export mappings and a bounded profile for realtime streams, transforms, leases and screen metadata. This is an architectural recommendation, not a WoT conformance claim. [WoT TD 1.1](https://www.w3.org/TR/wot-thing-description11/)

WoT Discovery separates introductions from authorized metadata exploration and supports local and global patterns. We should use scoped directories and native discovery adapters, returning incomplete results honestly. Wi-Fi attachment cannot guarantee enumeration of every device, its OS or its sensors. [WoT Discovery](https://www.w3.org/TR/wot-discovery/)

Measured values should carry explicit units rather than reuse joystick ranges. UCUM is an appropriate interoperable unit representation; coordinate frames, calibration and uncertainty still need separate fields. [UCUM](https://ucum.org/ucum)

## Transport decisions

These are recommendations based on protocol properties. No comparative latency benchmark was performed.

| Transport | Role in the platform | Reason and constraint |
| --- | --- | --- |
| WebRTC | First peer transport for browser/native interaction; encoded media tracks | Reuse the working integration. Data-channel reliability is configurable; internet connectivity needs ICE and often TURN. [WebRTC](https://www.w3.org/TR/webrtc/), [Data channels](https://www.rfc-editor.org/rfc/rfc8831.html) |
| WebTransport | Optional browser-to-edge path | Negotiate available streams/datagrams and runtime support; it does not supply peer rendezvous or a media application by itself. [WebTransport](https://www.w3.org/TR/webtransport/) |
| WebSocket over TLS | Signaling, control, compatible gateway transport | Reliable ordered delivery needs application queue/age bounds for interactive data. [WebSocket](https://www.rfc-editor.org/rfc/rfc6455.html) |
| Native QUIC | Optional native/embedded gateway path | Streams and datagrams share established security/congestion mechanisms; UDP reachability still matters. [QUIC](https://www.rfc-editor.org/rfc/rfc9000.html), [Datagrams](https://www.rfc-editor.org/rfc/rfc9221.html) |
| MQTT 5 | IoT telemetry and commands through a connector | QoS is delivery behavior; it is not physical-effect proof. Expiry and authorization remain necessary. [MQTT 5](https://docs.oasis-open.org/mqtt/mqtt/v5.0/os/mqtt-v5.0-os.html) |
| OPC UA / ROS 2 | Industrial/robot edge connectors | Preserve the native information model, quality and QoS while exporting selected resources. [OPC UA concepts](https://reference.opcfoundation.org/specs/OPC-10000-1/4), [ROS 2 QoS](https://design.ros2.org/articles/qos) |

Readable JSON descriptions and standard CBOR envelopes are a useful extensible baseline; compact negotiated profiles are appropriate for common fast samples. This does not select one fixed payload size for every device. [CBOR](https://www.rfc-editor.org/rfc/rfc8949.html)

Authentication must bind participants and endpoints as well as encrypt transport. Internet signaling needs HTTPS, scoped authorization and relay credentials; the current HTTP Hub cannot become internet infrastructure by being hosted unchanged. Use established crypto/identity libraries. Sender-constrained OAuth tokens are one candidate for the future control service, with replay protections implemented as required by that protocol. [WebRTC security](https://www.rfc-editor.org/rfc/rfc8827.html), [OAuth DPoP](https://www.rfc-editor.org/rfc/rfc9449.html)

## Gateway and algorithm patterns

| Pattern | Pipeline | What can be verified |
| --- | --- | --- |
| Phone trackpad | Touch contacts → relative-pointer transform → application pointer or native OS sink | Application pointer movement and native OS pointer movement need separate acceptance |
| Old IR appliance | Authorized command → nearby gateway → configured IR pattern | Emission; effect only with target reply or independent feedback |
| Mechanical switch | Gateway → actuator → physical switch, with separate limit/state sensor | Command acceptance and observed state; gateway enforces limits/watchdog |
| Zigbee appliance | Enrolled coordinator/bridge → normalized resources | Device/profile features exposed by that bridge |
| Industrial telemetry | Explicit gateway → CAN/Modbus/OPC UA profile → unit-aware sample | Source quality/time and known register/profile interpretation |
| Camera control | Local frames → pose → gesture → application action | Processor version, inputs, freshness, outputs; lens ownership alone does not prove gestures |
| Table tap / sound fusion | Microphone/motion → opt-in fusion processor → event | A particular algorithm must declare required sensors and pass its own accuracy tests |
| Terminal operation | Explicit native agent → approved terminal session/tool | Separate execution permissions, credentials and local audit; descriptor text is never execution authority |

An acknowledgment reports its evidence level: router receipt, policy acceptance, adapter dispatch, target reply, or observed effect. Transmit-only devices may finish with `unverified`; retries of toggle or other non-idempotent commands must preserve uncertainty.

## Test coverage model

Support progresses through `researched → implemented → contract-tested → runtime-tested → physical-verified`, with exact versions and evidence attached. A source link, emulator or protocol simulator cannot stand in for physical proof.

Representative suites cover browser/native permission denial and backgrounding; watch companion identity and reconnection; headset route changes; media codecs and slow sinks; wrong units/calibration/profile; unknown feedback; motor watchdogs; ownership conflicts; stale/replayed/foreign-session packets; plugin permission escalation; and direct versus relayed internet paths.

The common contract can cover new device families without claiming every model is tested. Certification is per connector/profile/runtime combination, with model-specific receipts when behavior differs.
