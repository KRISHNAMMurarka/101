## Native bridge admission repair

Independent review found that the actual JS producer posts native send without synchronously increasing bufferedAmount. A faithful producer-buffer-zero regression reproduced two same-turn 262144-byte sends crossing a 262144-byte raw limit. A zero-payload flood also reproduced unbounded native bridge submissions. Both were RED before their fixes.

The adapter now reserves cumulative payload bytes and message count before native send. Its bufferedAmount is the larger of the observed valid native snapshot and submitted payload bytes minus credited bytes; malformed native snapshots fail closed. Every channel also has a fixed 256-pending-message bound, including empty strings and zero-length buffers. Failed bridge calls retain their uncertain reservations. These bounds cover JS/native-bridge outstanding payloads and commands plus the observed RTC channel buffer snapshot. They do not claim a bound on every SCTP/network/runtime allocation or peer effect.

Only explicit caller-owned getStats refresh can retire reservations. Valid monotone safe-integer bytesSent/messagesSent must stay within submitted totals and advance coherently. Credit applies exclusively to locally created channels with a valid negotiated native channel id (zero is valid), matching report dataChannelIdentifier and label, a unique stable stats id, and the same live adapter/channel owner. Duplicate ids, reused/closed ids, changed report identities, stale completions, incoming channels, missing/malformed/regressing counters and absent stats cannot transfer credit. No native buffered event or timer implies drain; the adapter owns no timer. Underlying producer channels are exclusively owned by this port once injected.

Installed native Android/iOS wrappers serialize all native statistics fields. The upstream WebRTC M124 branch6367 collector emits data-channel id/label/dataChannelIdentifier/bytesSent/messagesSent, and its SendDataMessage increments both sent counters only after successful controller SendData. These counters prove native SCTP handoff, never receiver receipt/effect. Source references: [M124 channel send](https://webrtc.googlesource.com/src/+/refs/branch-heads/6367/pc/sctp_data_channel.cc), [M124 stats collector](https://webrtc.googlesource.com/src/+/refs/branch-heads/6367/pc/rtc_stats_collector.cc). Installed native bindings use JitsiWebRTC/org.jitsi WebRTC124; physical report availability and network/runtime buffers remain qualification requirements.

Repair selector: 18 focused adapter tests GREEN after same-turn payload, zero-message and inconsistent-counter REDs. Added matching cumulative credit, missing stats, wrong ids/labels, regressing/changing counters, id reuse/collision, pre-negotiation null ids, incoming no-credit, bridge uncertainty and closed-peer stats cancellation checks. Native UI owns one-flight 250ms stats refresh and visibly stops on absent measurements or rejected driver admission rather than silently resurrecting output.

Root re-review repair: a faithful malformed owned report with bytesSent=0/messagesSent=256 after 256 one-byte sends reproduced an incorrect 257th admission (RED “Missing expected exception”). Root retains a bounded cumulative byte endpoint for each outstanding submitted message (at most 256 entries), and credits a report only if its paired bytes/count describes that exact submitted FIFO prefix. Valid empty-message prefixes advance count without bytes. Invalid paired counters leave every reservation in place; credited prefixes are retired. The additional regression covers both the malformed one-byte prefix and legitimate empty-message advances. Physical collector availability/queue behavior remains open; no counter assumes receipt.
