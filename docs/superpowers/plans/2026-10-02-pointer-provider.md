## Scope and design

The existing typed bridge and surface are real callers. Add a pure shared `PointerSourceDriver` to keep relative movement, capture time, contact heartbeat and release identical across browser/native UI. Root integrates its exports/profile declarations and owns UI/pairing/native factory/evidence. An internal worker owns only driver source/tests and a lane execution record. No platform package imports game code.

Relative input stores normalized absolute position (default center), one active touch anchor and pointer ID. Begin sends contact true and establishes a local anchor without moving the target. Move accumulates dx/padWidth,dy/padHeight into clamped absolute state. Repeated move, lift/recontact, opposite diagonals and pad/receiver resize retain target position. Disposable loss never discards incremental state: each later send is recoverable absolute position. Contact uses reliable current-state events and periodic heartbeat. A captured change that has not been admitted keeps its original capture time; a later heartbeat cannot relabel that change as newly captured for latency.

Driver interface: `new PointerSourceDriver({publish:(capability,value,{capturedAt})=>boolean,now:()=>number,positionCapability?:string,contactCapability?:string,initial?:{x,y},sampleHz?:number,heartbeatMs?:number})`; methods `begin(pointerId,x,y,width,height):boolean`, `move(pointerId,x,y,width,height):boolean`, `end(pointerId):boolean`, `nudge(dx,dy):boolean`, `setContact(active:boolean):boolean`, `release():void`, `tick():void`, `stop():void`, `state():Readonly<{position:{x,y},contact:boolean,stopped:boolean,lastAdmission:boolean}>`. IDs nonnegative safe integers; all geometry/input finite with positive dimensions. sampleHz 1..60 default60 bounds all position attempts including heartbeat; heartbeat 20..50ms default50 and incompatible `1000/sampleHz > heartbeatMs` is rejected. Current contact repeats even false while active so receiver retains an available route. No owned timer or DOM/native imports. Constructor captures callbacks/options; stop is terminal, clears anchor and publishes reliable false once if possible. Clock failure/backward time releases and stops. Invalid events and unrelated touches cannot move or refresh state. Publish rejection is exposed, never represented as receipt/effect. Valid coalesced local updates can return true without publication; `lastAdmission` records only the last individual callback result.

The browser caller uses React pointer events plus keyboard arrows and Space, ResizeObserver for the receiver canvas, visible focus/status/stop and blur/hide/unmount release. A lab keeps raw diagnostics and manual pairing details in a developer surface; product controls use plain labels and monochrome chrome. No public preview or external hosting. Real source event tests run through the local page rather than only injected publisher values. Native caller uses the same general driver/publisher and a deliberate RTC factory/adapter, rather than normalized 101 InputFrame. Existing native game controller remains compatible.

General pairing stays separate from resource consent: selected peer/enrollment epoch scopes the connection; owner approval selects resource profiles. Raw SDP exchange proves encrypted WebRTC only with the actual trust topology documented. Do not call it authenticated endpoint enrollment merely because constructor IDs or a QR/code exist. S02/S04 and T04 close only with actual identity binding/verification evidence. Browser/native resource readiness reports actual API availability; permission/foreground loss stops outputs. Physical T08/T14 needs exact iPhone and Android runs, both diagonals/contact/resize/no anchor and capture-to-render distributions with clock bounds. Missing hardware/person actions remain explicit; simulations do not close those rows.

## Native RTC preflight decision

Installed react-native-webrtc is the actual producer. Its JS channel getters are optional numbers. Android creation emits -1 for unset; the installed iOS uint16 getters wrap that value to 65535. The host explicitly selects the producer sentinel. Normalize iOS 65535 only when this adapter created the channel with the corresponding delivery option omitted; explicit finite65535 and incoming65535 cannot prove reliable delivery and remain finite. General browser channels expose null. Unknown/missing/invalid semantics stay incompatible. Binary events already produce ArrayBuffer in this library, and send handles ArrayBuffer/views. Do not infer ordered/retransmission properties from a label. Initial iOS -1 assumptions were disproved by the actual simulator creation failure and repaired with a faithful RED/GREEN fixture.

Android's incoming-channel notification currently hardcodes ordered=true and both limits=-1 rather than reporting the remote negotiated properties (`PeerConnectionObserver.java` around371). The first Android general source must therefore initiate and create its own two channels; the browser surface is responder. Do not ship an incoming-native disposable path by relabeling it as lossy. This producer defect and explicit source-only topology stay in qualification limitations until a faithful API or verified upstream fix exists.

Before implementing the native adapter, narrow the raw package's RTC factory contract to the fields it actually consumes: connectionState/iceGatheringState/localDescription, owned connection/channel callbacks, SDP methods, getStats, ice event subscription, createDataChannel and close; data channel label/delivery/buffer/state/send/message/close/error and binaryType/lowThreshold. Browser RTCPeerConnection structurally conforms; callback types may use explicit method variance to accept richer native/browser events while consuming only documented channel/data fields. A pure native adapter accepts an injected producer/factory so Node tests can validate real producer-shaped metadata, description conversion, event/data forwarding, teardown and listener cleanup without importing React Native. No fake normalization of unknown properties or full DOM-object assertion supplies a capability. Root integrates the actual React Native factory only after these tests.

## Caller design pass

Existing palette: ground #0A0A0A, pad #101010, text #F2F2F2, light ground #FFFFFF and light pad #F7F7F7; secondary text and control edges use existing contrast-qualified tokens. Browser uses the self-hosted Geist 101 family and existing type scale; native uses the system family and shared theme roles. No external font/service dependency. The one dominant element is the touch pad/application surface. A quiet row above it chooses source or receiver and shows Stop; the hand-transfer details expand below, rather than splitting the primary control into repeated cards. Left-aligned instructions stay short and grouped with the action they explain. On narrow screens the primary surface fills the available width and directional controls wrap. The application marker changes weight with contact and follows input directly; no decorative animation.

Reviewed against the pointer job: no hero marketing, statistics cards or decorative grid. A simple frame indicates the bounded surface and a central target indicates the remote output; both carry actual interaction meaning. The source pad starts at the center independently of initial finger position. Keyboard and labelled directional controls offer equivalent movement/contact, with visible focus and immediate release on blur/hide/unmount. Pairing code fields and identity limitations belong to the explicitly labelled lab. Browser remains responder for native-originated offers to preserve actual Android channel delivery metadata.
